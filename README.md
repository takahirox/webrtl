# webrtl

WebRTL compiles edited Verilog into a new WebAssembly circuit entirely in your
browser. The GitHub Pages site needs only static assets. The original trusted-local
Verilator/Emscripten development mode remains available separately.

## Public browser compiler

Demo URL: **https://takahirox.github.io/webrtl/** (published after the Pages workflow
successfully deploys `main`). Edit the supplied RTL and click **Compile**. The first
compile downloads the toolchain; progress and errors appear below the editor,
and successful compiler output is available under **Compiler diagnostics**.

The browser starts with the original single-file counter. Use the **Verilog project**
controls to work with multiple sources:

1. Enter a filename and click **Add file**, or use **Import local .v files** to
   select multiple files at once. Imports add files to the current project.
2. Choose a **Source file** to edit. Edits are kept when switching files. Enter a
   new filename and click **Rename file**, or click **Remove file** to remove the
   selected source. Renaming a file does not rename modules or their references.
3. Enter the exact, case-sensitive HDL module name in **Top module**. This is a
   module name, not a filename; all project files are passed to the browser compiler.
4. Click **Compile**, then use the simulation controls below. File or top-module
   changes discard the old simulation; switching the selected file alone keeps it.

For a small multi-file demonstration, choose **Two-file counter** and click
**Load example (replaces project)**. The top module `split_counter` in
[split-counter.v](examples/split-counter/split-counter.v) instantiates `counter_next`
from [counter-next.v](examples/split-counter/counter-next.v). Compile and Step to 1.
Select `counter-next.v`, change `current + 8'd1` to `current + 8'd3`, compile again,
and Step to 3 then 6. The output comes from the newly generated WASM circuit, with
both source files compiled together. Choose **Single-file counter** and load it to
return to the original example. Loading an example replaces all current sources;
projects are held only in memory and are lost on reload.

Invalid names, duplicate imports/renames, or imports exceeding the size limit are
rejected without replacing existing files. Import batches are atomic: if any file
fails validation, none are added. Compilation errors retain all sources and the
chosen top module so you can fix and retry. Missing modules and Verilog errors
include the existing Yosys diagnostics.

The **Example** selector also supplies RTL video and audio designs. Load Video
to render a 64 × 48 RTL color pattern on Canvas, or load Audio
to play mono PCM generated by RTL after clicking Run. Edit their RTL to change
the image or tone. See the [output contracts and usage guide](docs/output-interfaces.md)
for ports, timing, batching, playback controls, audio unlock, and limitations.
These interfaces are available in the static browser mode; trusted-local mode
retains the counter.

For Counter, use **Step** for one full clock cycle, **Run** for approximately
10 cycles per second, **Pause** to stop, and **Reset** to pause and clock the reset input.
With the original example, Reset yields 0 and Step increments modulo 256. Change
`count + 8'd1` to `count + 8'd3`, compile, and Step yields 3 then 6. The value comes
from the newly generated Wasm circuit. Editing or compiling terminates the previous
simulation; each successful compile initializes and resets a fresh model. A failed
compile leaves simulation disabled; fix the source and compile again.

### Build and preview the static site

Use Node.js 22+ and Python 3.10+:

```sh
npm ci
npm run build:demo
python3 -m http.server 8000 --bind 127.0.0.1 --directory .build/pages
```

Open **http://127.0.0.1:8000/webrtl/**, including the trailing slash. No native HDL
compiler, Emscripten SDK, compilation API, or `server.py` is needed for this build
or for users' edits. The build copies the pinned YoWASP packages from `node_modules`
into the static artifact; it never compiles the example HDL. All URLs are relative,
including worker, compiler Wasm, runtime headers, and example URLs, so the same
artifact works under the GitHub Pages project subpath.

[build_site.py](build_site.py) replaces `.build/pages/webrtl/` only after staging
succeeds. The artifact contains the UI, example source, compiler and simulator
workers, C++ board adapter, toolchain notices, and `tools/` (Yosys/Clang JS, Wasm,
resources, and matching CXXRTL headers). There is no precompiled circuit. Generated
site assets are ignored by Git; `package-lock.json` pins toolchain integrity.
Rebuild after changing the UI, adapter, or dependencies.

### Browser architecture and tool selection

```text
Editor project {files, top}
  → compiler Web Worker: YoWASP Yosys → generated CXXRTL C++
                       → YoWASP Clang/LLD → new sim.wasm bytes
  → terminate compiler worker
  → simulator Web Worker: instantiate sim.wasm → reset/step/batch/read outputs
  → UI displays count, draws RTL frames, or plays RTL PCM
```

[compiler.js](web/compiler.js) accepts project files and a top-module name, operates
in the tools' in-memory virtual filesystems, and returns newly compiled Wasm bytes.
The project UI passes its complete source map and chosen top to this same pipeline;
modules can be in separate files or share a file. The selected **Output interface**
chooses the required ports independently of the top-module name.
[browser-simulator.cpp](web/browser-simulator.cpp) is the small selectable adapter
for the documented counter/video/audio contracts; it drives clock/reset and batches
outputs from the generated model. It contains no counter, pattern, or tone
implementation. The runtime worker
supplies no filesystem/network imports to the circuit and rejects WASI I/O.

The compiler worker is terminated on success, failure, or timeout. Its C++ and
virtual filesystem disappear; only the Wasm result moves to a fresh runtime worker.
The runtime is terminated on editing/recompilation or execution errors. Simulation
requests are serialized, with a watchdog for stalled circuits. The UI schedules
steps and displays results; it does not evaluate Verilog or emulate the counter.

Existing OSS was evaluated before choosing this path:

- [Vera](https://github.com/roman01la/vera) demonstrates browser Verilator →
  Emception Clang → Wasm. Reusing that route would require maintaining its
  Verilator build and Emscripten sysroot integration here.
- [YoWASP](https://yowasp.org/) distributes browser-ready Yosys and Clang/LLD
  packages with a [common virtual-filesystem API](https://github.com/YoWASP/runtime-js).
  The pinned Yosys CXXRTL backend plus Clang provides the required synthesizable
  cycle simulation without a custom HDL compiler or native toolchain build.
  This is the selected route. It differs from the local Verilator frontend, so its
  supported HDL and diagnostics differ too.

All runtime dependencies are hosted with the site; there is no CDN dependency.
Only static GET requests download the tooling. HDL, generated C++, and compiled
circuits are never uploaded to a compilation service, GitHub Actions, or another
remote endpoint. They stay in browser memory, with no project persistence yet.
Tool downloads may remain in the browser's normal HTTP cache. Toolchain license
texts ship in [third-party-notices.txt](web/third-party-notices.txt).

### Browser support and limits

- **Desktop Chromium and Firefox** are covered by the real-compiler Playwright
  suite (tested here with Chromium 156 and Firefox 157 bundled by Playwright 1.64.1).
  Use a current browser with ES modules, module workers, WebAssembly and its
  compiler-required features enabled. Safari/WebKit and mobile browsers have not
  been validated. No SharedArrayBuffer, cross-origin isolation headers, special
  browser flags, or compilation backend is required.
- **Filenames** are flat, case-sensitive names ending in lowercase `.v`. Start
  with a letter, digit or underscore, followed by letters, digits, underscores or
  hyphens (for example `counter-next.v`). Paths, spaces, leading hyphens, other
  punctuation, and duplicate filenames are rejected. No directory/project import
  or include-tree resolution is provided. The `.v` extension also applies to the
  supported subset of SystemVerilog.
- **Top-module names** start with an ASCII letter, followed by ASCII letters,
  digits or underscores. Enter the declared module name exactly; it need not match
  a filename. Escaped identifiers are unsupported. The Counter interface requires scalar
  input **`clk`**, scalar active-high input **`reset`**, and unsigned 8-bit output
  **`count`**, with no extra ports. Interface mismatches report an error before C++
  compilation. Reset follows the edited circuit's RTL; it does not force zero
  independently of that circuit. Arbitrary top-level I/O, CPU bus/register adapters,
  and ROM/RAM loading remain follow-up work. Video and Audio use their documented
  [output contracts](docs/output-interfaces.md) with any valid top-module name.
- Supports Yosys's synthesizable Verilog and limited SystemVerilog frontend:
  arithmetic, bitwise/combinational logic, edge-triggered registers, synchronous
  and asynchronous resets, and internal module instances. This is a two-state,
  cycle-based CXXRTL simulation, not a full event-driven language simulator.
  Unknown/high-impedance values and uninitialized state do not have full four-state
  semantics. HDL timing delays, testbench tasks, DPI, external C++, filesystem I/O,
  external includes, arbitrary project imports, assertions and full SystemVerilog
  are outside this milestone. Yosys may ignore simulation-only constructs; use
  synthesizable clocked logic and inspect diagnostics.
- At most **64 KiB total UTF-8 source** across all project files, with nonempty
  source in every file at compile time, and one compile at a time. Imports are
  checked against the total limit before adding files; edited source is checked
  on Compile. Compilation, including downloads, has a **120-second** deadline.
  A simulation request has a
  **10-second** watchdog. Timeout terminates the relevant worker and permits a new
  compile. Timer throttling in background tabs can delay both simulation and
  watchdogs. Counter targets 10 cycles/second; video/audio use the explicit
  [simulation rates and bounded batches](docs/output-interfaces.md#transfer-bounds-and-performance).
- Static compiler assets total approximately **185 MB uncompressed** (Yosys about
  79 MB; Clang/sysroot about 105 MB), plus small UI/header assets. Network transfer
  depends on hosting compression and caching. First load may take tens of seconds
  on an ordinary connection, and slow downloads can hit the deadline. Local
  loopback first compilation measured about **2.5 seconds** in Chromium on this
  development machine; this is not a network or cross-device performance promise.
- Compiler memory can reach hundreds of MiB or more; use a desktop with several
  GiB available. Compiler peak memory has not been measured and is limited by the
  browser/engine rather than an application-enforced heap cap. Large/pathological
  designs can exhaust it and cause a worker or tab to fail. The generated simulator
  has a **64 MiB** Wasm memory maximum. Fresh workers release old compiler/model
  allocations rather than retaining all compiled designs.

### GitHub Pages deployment

One time, in **Settings → Pages → Build and deployment**, select **GitHub Actions**
as the source. Allow `main` in any `github-pages` environment branch restrictions.

[The Pages workflow](.github/workflows/pages.yml) runs on PRs and pushes to `main`,
and manual dispatch. It installs the native reference toolchain only for the
separate trusted-local regression test, installs pinned browser tools with `npm ci`,
and runs Python tests and real-circuit browser tests in both modes. The static
suite uses Chromium and Firefox under `/webrtl/`. The tested
`.build/pages/webrtl/` contents are uploaded directly as the Pages artifact; uploading
the parent directory would add an unwanted URL segment. Only `main` deploys, with
scoped Pages permissions. Actions assemble the app and toolchain; they never
compile each user's HDL.

**Required post-merge verification for #8:** after deployment, open the public
site in a fresh browser context, compile the original RTL and check Reset=0 and
Step=1, then change the increment to `8'd3`, compile, and check Step=3 then 6.
Check Run/Pause/Reset and syntax-error recovery. Confirm requests stay under
`/webrtl/` and only download static assets. This live deployment check remains
pending until deployment; local pre-merge tests do not prove publication succeeded.

**Required post-merge verification for #12:** after deployment, open the public
`/webrtl/` site, load and compile the two-file counter, and confirm Step=1. Change
`current + 8'd1` to `current + 8'd3` in `counter-next.v`, compile again, and confirm
Step=3 then 6 and working Run/Pause/Reset. Record the public-site result separately.
This check is pending deployment; local static-site tests are pre-merge evidence only.

## Local setup

Use Python 3.10+, Verilator 5+, and Emscripten 3.1.6+ with `verilator` and `em++`
on `PATH`. No Python packages or frontend dependencies are needed to run this local mode.
Ubuntu 24.04 packages are the reference native toolchain. Verilator 5.052 with
Emscripten 6.0.13 has a known CPU-affinity symbol link failure; use the reference
Verilator 5.020 toolchain if affected. This does not affect browser compilation.
On Ubuntu 24.04:

```sh
sudo apt-get update
sudo apt-get install python3 verilator emscripten
```

On macOS with Homebrew:

```sh
brew install python verilator emscripten
```

Alternatively install the [Emscripten SDK](https://emscripten.org/docs/getting_started/downloads.html)
and activate its environment in the same terminal as the service. Verify the
toolchain, then start the service from the repository root:

```sh
verilator --version
em++ --version
python3 server.py --trusted-local
```

Open **http://127.0.0.1:8000** in a modern desktop browser. The page loads
[examples/counter.v](examples/counter.v). Edit it if desired, then click **Compile**.
The first compilation may take longer while Emscripten initializes its cache.
Build errors appear below the editor; fix the source or toolchain and retry.

- **Step** evaluates low → high → low on `clk`: one complete clock cycle.
- **Run** advances that same model at approximately 10 cycles per second.
- **Pause** stops advancement, preserving circuit state.
- **Reset** pauses, clocks with `reset` asserted, then deasserts it. The provided
  counter returns to zero; its next Step produces one. It wraps from 255 to zero.

Editing or recompiling stops and discards the previous simulator. Each successful
compile starts a fresh circuit and resets it. Reset also works while running.
Use `--port 8001` if the default port is occupied. Stop with Ctrl-C; temporary
build artifacts are removed on normal shutdown.

## Trusted-local build and simulation boundaries

```text
Editor → POST /api/build {"source": "…"}
       → Verilator C++ model → Emscripten → sim.mjs + sim.wasm
       ← {"moduleUrl": "/builds/<unique-id>/sim.mjs"}
Browser imports the module and executes the WebAssembly model locally.
```

[build.py](build.py) accepts one source string and an output directory. It uses
[Verilator's C++ generation](https://verilator.org/guide/latest/verilating.html),
then compiles the generated model, Verilator runtime, and
[simulator.cpp](simulator.cpp) with Emscripten. Emscripten's
[modularized ES module output](https://emscripten.org/docs/compiling/Modularized-Output.html)
exports an asynchronous factory. The resulting instance exposes `_sim_init()`,
`_sim_step()`, `_sim_reset()`, `_sim_count()`, and `_sim_destroy()`.
Initialization creates and resets the model; destruction finalizes and frees it.
Initialize before any step/reset/read, and do not use an instance after destruction.
The browser reads `count` through `_sim_count()` directly from the circuit model.
JavaScript schedules clock steps and displays values; it does not implement the
counter. Each half-cycle advances the model's time by one tick.

[server.py](server.py) serves a fixed set of UI files and generated artifacts,
and adapts that build function to HTTP. Build failures return a non-2xx JSON
`{"error": "…"}` response with tool diagnostics (the final 16 KB). Successful
modules and their sibling Wasm files have unique URLs and the appropriate MIME
types. This HTTP response and the small simulation API are the integration
boundaries for the local backend. The service never runs the simulator.

To build the same example independently of the web service:

```sh
python3 build.py examples/counter.v .build/counter
```

This produces `.build/counter/sim.mjs` and `.build/counter/sim.wasm` along with
intermediate sources and diagnostics. Load the module over HTTP rather than
opening it with `file://`.

## Trusted-local supported input and limitations

- A single source file with top module **`counter`**, scalar inputs **`clk`** and
  **`reset`**, and unsigned 8-bit output **`count`**. Preserve this interface when
  editing. Missing ports produce C++ wrapper compilation errors. Reset is
  active high; the supplied design uses a rising-edge synchronous reset.
- Clock-driven, synthesizable Verilog supported by Verilator. This is not a full
  SystemVerilog environment. Timing controls/delays, multi-file projects, external
  includes, DPI, file I/O, and user C++ are unsupported. Verilator warnings fail
  the build; fix the reported issue instead of suppressing warnings globally.
- Edited circuits follow their own RTL semantics. The provided example defines
  the increment-by-one and reset-to-zero behavior; the wrapper does not impose it.
- Single-threaded simulation on the browser's main thread, with no waveforms or
  arbitrary signal explorer. Run speed follows browser timer scheduling and may
  slow in background tabs. A pathological model can hang a tab.
- At most 64 KiB of HDL, one compilation at a time, and a 120-second total build
  timeout. Compiled modules may grow Wasm memory to 64 MiB. Successful build
  directories remain until service shutdown; restart to reclaim disk space.

## Trusted-local trust boundary

**This is a development-only build service for trusted local HDL.** Starting it
requires `--trusted-local`, and it binds exclusively to `127.0.0.1`. Host checks
reject DNS rebinding; compilation requires a same-origin JSON request from the
local UI. There is no CORS opt-in. Only the fixed UI files and named build
artifacts are served, not the repository or intermediate tool output.

These checks are not a compiler sandbox or authentication. Native toolchains
process your HDL with the permissions of the service account; HDL directives or
toolchain vulnerabilities can access local resources. Only compile designs you
trust, including when using `build.py` directly. Do not expose the service through
a proxy, tunnel, public port, or shared host. Other local processes are trusted.

Public or multi-user hosting requires a separate isolated build worker with no
secrets or host filesystem access, restricted networking, and enforced CPU,
memory, process, disk, and execution-time limits, plus authentication and request
controls. The MVP's size check, timeout, and serialized builds do not provide
that isolation. Do not accept untrusted HDL on this service.

## Validation

The local browser integration test compiles real HDL with the installed native tools
and loads the resulting Wasm in Chromium. It checks reset, individual cycles,
255 → 0 wraparound, Run/Pause, Reset during Run, and recompilation after errors.
It also compiles a counter that increments by three and checks 3 then 6, proving
the displayed result follows the submitted circuit. Python tests cover request
validation, build error reporting, artifact access, and local-origin checks.

With the runtime toolchain installed, use Node.js 22+ for the test dependencies:

```sh
npm ci
npx playwright install --with-deps chromium firefox
npm test
```

The local browser test starts and stops its own trusted local service on port 8765.
The static tests assemble the compiler, serve only `.build/pages/` on port 8766,
and load `/webrtl/` in Chromium and Firefox. They observe real newly generated Wasm
bytes and differing circuit outputs, 255 → 0 wraparound, Run/Pause/Step/Reset,
recompilation during Run, source edits, syntax errors, interface errors, missing
tooling and recovery, the two-file example with a chosen top and edited helper,
file switching/add/rename/remove, atomic multi-file imports, invalid and duplicate
filenames, total source limits, missing top modules, UI heartbeats during compilation,
and same-origin static GET requests without a build API. The video/audio suite
also checks edited RTL pixels and PCM, precise framing/sample timing, real
Web Audio processing, unlock failure recovery, and output lifecycle/bounds.
These checks run before merge without a live Pages deployment. To run either mode separately:

```sh
npm run test:local
npm run test:demo
```

The static checks need only Node, Python, the npm packages, and installed Playwright
browsers; native Verilator and Emscripten are needed only for `test:local`.

On headless Ubuntu hosts without sound hardware, Firefox also needs a running
audio backend. The Pages workflow installs `pulseaudio` and runs these commands
as the test user before `npm test`:

```sh
pulseaudio --start --exit-idle-time=-1
pactl load-module module-null-sink sink_name=webrtl_ci rate=48000
pactl set-default-sink webrtl_ci
pactl list short sinks
```

The virtual sink supplies an output device; the tests still process RTL PCM
through real Web Audio and assert non-silent analyser output.

Python checks can also run alone without the compiler or Node:

```sh
python3 -m unittest discover -s tests -v
```

For a manual check, compile the unmodified example, Step to 1, Run then Pause,
verify the value stops changing, Reset to 0, and Step to 1 again. Edit the
increment to `8'd3`, compile, and verify each Step advances by three. Introduce
a syntax error and confirm the UI shows the tool diagnostic and disables simulation.
Testing additional desktop browsers and measuring speed are optional.
